# Fork agent instructions

Read `CLAUDE.md` before working in this repository. Its upstream engineering guidance applies except where this file overrides it. Upstream Markdown describes upstream Paseo, not fork-specific behavior; check the fork's code, tests, and history for fork facts.

## Upstream upgrade workflow

**A target version is the complete request.** If the user says to upgrade to `X.Y.Z`, use the exact official tag `vX.Y.Z` and execute this workflow. Do not ask the user to repeat the workflow, choose an implementation, or provide an intermediate approval. If a step cannot be completed within these rules, report the exact blocker; do not widen scope to get around it. An upgrade request does not authorize staging, committing, pushing, dispatching remote CI, or publishing.

**Maintenance checkout write allowlist.** Work in `downstream/patch-build`; do not merge upstream, create a branch, or create or reuse a Git worktree for the upgrade. Edit `scripts/fork/upstream/*.patch` and `scripts/fork/upstream/series.json` directly. The only other tracked files that may change are CI entrypoints, routing inputs, and bootstrap files that the target demonstrably requires before patch replay. Name those paths and why they must change before writing them. All product changes, including fork-only additions and their tests, belong in the patches. Do not copy, edit, move, or delete product files or upstream Markdown snapshots in the maintenance checkout. Existing direct product files, cache files, and tooling design changes are separate work; do not migrate or clean them up as part of an upgrade.

**Keep validation out of the user's Git repository.** Use an isolated temporary directory outside the checkout for fetches, preflight, replay, installation, builds, tests, and logs. Verification output, including the effective source tree, must not enter the user's checkout, any of its worktrees (including `.dev/fork-build`), Git object database, refs, or indexes. If the preflight tool needs Git metadata or a temporary index, give it a disposable, independent repository outside the checkout; do not share the user's object database or indexes. Export the effective tree into a plain directory for builds and tests; do not stage it in a checkout. Do not run `materialize`, `run`, `refresh`, `update`, or `ci-apply` against the user's repository for an upgrade. Inspect any writer's target and effects before running it. If the tools cannot respect this boundary, stop and report what could not be verified.

1. **Pin an explicit official target.** Read `scripts/fork/upstream/series.json` for the current baseline. Verify the selected release tag and its peeled commit against `getpaseo/paseo`; fetch the exact ref into the isolated verifier, not the user's repository. Run `node scripts/fork/upstream.mjs check --upstream <tag>` there against the current patch store and direct CI inputs. Do not use implicit latest-release selection.
2. **Resolve conflicts and failures from evidence.** Compare the affected paths and history at the old pin, the official target, and the fork. Classify the problem as upstream-existing, fork-introduced, introduced by the upgrade interaction, or unresolved. A red job alone does not establish provenance. Search official follow-up commits and PRs for the same failure, including changes outside the target release's ancestry. Before editing, state the classification, compared refs and paths, applicable upstream fix (if any), and chosen repair. If unresolved, keep investigating rather than patching speculatively.
3. **Adapt the patches directly.** Prefer an applicable official fix, including its required dependencies and behavioral coverage, while preserving fork features it does not supersede. Name any concrete incompatibility before adapting the official fix. If none applies, say what was searched and why a fork-specific change is necessary. Do not delete tests, restore removed configuration, or add retries or timeouts just to make CI green.
4. **Advance the pin and required build inputs together.** Update `series.json` to the selected official tag and commit with its rebased patches. GitHub Actions reads its workflow definitions and routing inputs before `ci-apply`, so a patch cannot replace an entrypoint that must exist at that stage. Apply only the direct changes justified under the allowlist above; keep other changes in patches.
5. **Verify the effective tree and report CI coverage.** In the isolated verifier, run `node scripts/fork/upstream.mjs check` against the new pin, then run the affected checks and tests on the exported effective tree. Cover both an applicable fork release tag and the bare package version where behavior differs. Review GitHub Actions only for a run covering the exact upgrade commit; verify `checkout → ci-apply → install → build/test` and report failed, skipped, canceled, and not-triggered jobs across all relevant workflows, including the latest attempts. If the upgrade has not been pushed or CI has not run, report that; never substitute old or upstream runs for the fork upgrade.

**Cleanup is not rollback.** Delete only this upgrade's isolated verification directory and any specifically identified accidental outputs. Preserve the upgraded patches, matching pin, required CI/bootstrap changes, and all pre-existing user work. A request to clean up does not authorize reverting the upgrade; only an explicit request to revert the upgrade does. Do not use a broad reset, clean, or restore as cleanup.

Apply steps 2 and 3 to repairs discovered during or after the upgrade, even when patch replay succeeds. A post-edit explanation or a passing test does not replace the pre-edit evidence checkpoint. Change this `AGENTS.md` only at the user's explicit request.
